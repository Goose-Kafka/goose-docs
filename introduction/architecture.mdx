# Architecture

## Overview

```
Kafka Topic
    │
    ▼
┌───────────────────────────────────────────────────────────┐
│  Consumer Goroutine (1)                                   │
│  • Batch-poll: ReadMessage loop (up to MAX_POLL_RECORDS)  │
│    - First ReadMessage() blocks until a message arrives   │
│    - Subsequent ReadMessage() with 100ms timeout          │
│  • Schema deserialize (protobuf→JSON or JSON passthrough)  │
│  • Validate (CEL expressions)                              │
│  • Apply filter (JSONPath or CEL expression)              │
│  • Split polled messages into chunks of WORKER_POOL_SIZE  │
│  • Each chunk → separate Batch with UUID                  │
│  • Register offsets in OffsetManager                       │
│  • batchChan <- batch  ← BLOCKS if full (backpressure)    │
└─────────────────────┬─────────────────────────────────────┘
                      │  chan *Batch (buffered)
                      ▼
┌───────────────────────────────────────────────────────────┐
│  Worker Pool (N goroutines)                               │
│  • Worker reads <- batchChan                              │
│  • Check circuit breaker                                  │
│  • Push to sink (HTTP/gRPC/MongoDB/PostgreSQL/Redis)     │
│  • On failure: retry → DLQ → circuit breaker              │
│  • Signal batch done → OffsetManager                      │
└─────────────────────┬─────────────────────────────────────┘
                      │
                      ▼
┌───────────────────────────────────────────────────────────┐
│  Offset Manager + Commit Loop                             │
│  • Contiguity-gated commit (at-least-once delivery)       │
│  • Commit to Kafka every COMMIT_INTERVAL_MS              │
│  • Prunes committed offsets (no memory leak)              │
└───────────────────────────────────────────────────────────┘
```

## Key Design Decisions

### Channel-based backpressure
`batchChan <- batch` blocks the consumer when workers are busy. No spin loops, no CPU waste.

### Batch-poll consumer
Polls up to `MAX_POLL_RECORDS` messages per cycle using `ReadMessage` (not `FetchMessage` — which blocks forever with consumer groups). Polled messages are split into chunks of `WORKER_POOL_SIZE`, and each chunk is dispatched as a separate batch. Ordered mode (`POOL=1`) processes one message at a time in strict offset order; multi-worker mode (`POOL>1`) processes chunks in parallel.

<Callout type="info">
Benchmark (2026-09-28, 1 pod, 1 Kafka partition): **6,017 msg/s at 0ms sink delay, ~4,000 msg/s at 50ms, ~800 msg/s in ordered mode** — all with zero drops and 13–23 MiB memory. See [Load Test Results](/benchmarking/load-test-results).
</Callout>

### Contiguity-gated offsets
Offset N is committed only when all messages up to N are processed. Prevents skipping messages on crash.

### Connection TTL
Connections are closed after TTL and re-opened, redistributing traffic across backend pods. Fixes connection pinning.

### Auto-matched pool
`SINK_HTTP_MAX_CONNECTIONS` auto-matches `SINK_WORKER_POOL_SIZE` to prevent port exhaustion.

### Network error retry
TCP connection errors (status code 0) are always retried — never silently dropped.

## Sink Interface

All sink types implement the same `Sink` interface, selected at startup by `SINK_TYPE`:

```go
type Sink interface {
    Push(msgs []Message) ([]FailedMessage, error)
    Close() error
}
```
