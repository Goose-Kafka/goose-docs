# Worker Pool

| Env Var | Default | Description |
|---------|---------|-------------|
| `SINK_WORKER_POOL_SIZE` | `50` | Number of worker goroutines (concurrent sink calls) |
| `SINK_WORKER_POOL_BUFFER` | `10` | Batch channel buffer size (batches queued while workers busy) |

## Auto-Matched Connections

`SINK_HTTP_MAX_CONNECTIONS` automatically matches `SINK_WORKER_POOL_SIZE` at startup. This prevents port exhaustion — each worker gets a pooled connection.

<Warning>
If you set `SINK_WORKER_POOL_SIZE=100` but leave `SINK_HTTP_MAX_CONNECTIONS` at the default, Goose auto-matches them to 100. You only need to set one.
</Warning>

## Max Concurrent HTTP Requests

```
concurrent_requests = goose_pods × workers_per_pod
```

This is capped by Kafka partitions — you can't have more goose pods than partitions.

## Recommended Values

The following numbers are from the 2026-09-28 benchmark on a kind K8s cluster (1 pod, 1 Kafka partition, 3 mock-HTTP replicas). See [Load Test Results](/benchmarking/load-test-results) for full details.

| Config | Sink Delay | Throughput | Memory |
|--------|-----------|------------|--------|
| POOL=100, POLL=500 | 0ms | 6,017/s | 13 MiB |
| POOL=100, POLL=500 | 50ms | ~4,000/s | 23 MiB |
| POOL=1, POLL=1 (ordered) | 0ms | ~800/s | 21 MiB |

<Callout type="info">
These are single-pod numbers. Scale horizontally by adding pods (capped by Kafka partitions): `total_throughput = pods × per_pod_throughput`.
</Callout>

## Ordered vs Multi-Worker Mode

`SINK_WORKER_POOL_SIZE` controls both concurrency and ordering guarantees:

| Mode | Config | Behavior |
|------|--------|----------|
| Ordered | `SINK_WORKER_POOL_SIZE=1` | Strict Kafka offset order — safest, no dependency issues (~800/s @ 0ms) |
| Multi-worker | `SINK_WORKER_POOL_SIZE>1` | Messages within a chunk processed in parallel — max throughput (~6,000/s @ 0ms) |

<Warning>
If messages within a partition are dependent (e.g., m10 depends on m1 succeeding), you MUST use `SINK_WORKER_POOL_SIZE=1`. With multiple workers, m10's sink call might complete before m1's, causing data consistency issues.
</Warning>

See [Batch-Poll Consumer](/configuration/batch-poll) for the full comparison table and when-to-use guidance.
